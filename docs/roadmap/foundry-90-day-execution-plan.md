# Foundry 90-day execution plan

## Principle

Launch one coherent wedge before marketplace, certification, white-label scale, or always-on infrastructure:

> Build and deploy one useful AI-enabled service in seven days.

## Days 0–14 — consolidate and prove the route

- [x] Confirm `agentic-business-os` as canonical substrate.
- [x] Confirm `frankx.ai/foundry` is live and production-backed.
- [x] Audit GitHub estate and identify property vertical as the implementer reference.
- [x] Define customer routes, runtime matrix, proof loop, offer ladder, and community contract.
- [x] Add portable Pathfinder skill, agent, and command contracts.
- [ ] Add a public-safe kit manifest schema: license, support, security, tests, last verification, deployment evidence.
- [ ] Retire or clearly label the six broken standalone First Agent links.
- [ ] Upgrade and extract one current AI SDK 7/Eve Business Agent starter only after auth, tenant isolation, rate limits, spend caps, durable storage, and at least 10 evaluation cases pass.
- [ ] Run the Pathfinder on four internal scenarios: student, restart, agency, SME.
- [ ] Produce one complete seven-day proof packet from a real internal use case.

**Exit gate:** a new user can choose one route and produce a credible proof plan in under 20 minutes.

## Days 15–30 — build the open Foundry experience

- [ ] Add `/foundry/pathfinder` page spec and static first-read design.
- [ ] Build the deterministic diagnostic; an LLM may explain results but must not choose from unsupported facts.
- [ ] Publish the One Process → One Offer canvas.
- [ ] Publish the Architecture Chooser from the routing matrix.
- [ ] Add four audience routes: student, restart, founder, agency. Keep SME application-led initially.
- [ ] Connect each route to one starter repo and one proof packet.
- [ ] Add analytics events and claims ledger.
- [ ] Verify desktop, mobile, accessibility, reduced motion, performance, and Vercel preview.

**Exit gate:** 60% of internal test users reach one selected route and download/fork the correct artifact without explanation.

## Days 31–60 — validate paid guidance

- [ ] Deliver a small Foundry Sprint pilot manually.
- [ ] Cap cohort size to real review capacity.
- [ ] Use artifact-first onboarding and Friday proof cells.
- [ ] Record support time, common blocks, deployment failures, and evaluation failures.
- [ ] Convert repeated help into skill/agent/runbook improvements.
- [ ] Verify checkout, entitlement, delivery, onboarding, refund, and support recovery before public pricing.
- [ ] Collect case-study permission separately from delivery.

**Exit gate:** at least three participants complete a proof packet; support cost and delivery scope are understood. This is a validation target, not a public demand claim.

## Days 61–90 — productize one vertical operator path

- [ ] Choose one vertical based on proof and founder access, not market-size speculation.
- [ ] Generalize the property template's partner implementation kit and readiness cockpit.
- [ ] Draft a formal operator license for qualified legal review.
- [ ] Add client-intake, privacy, claims, release, and managed-ops boundaries.
- [ ] Run one operator rehearsal in a clean repository.
- [ ] Add upstream update and rollback evidence.
- [ ] Decide whether a Foundry Circle pilot has enough repeated practice to justify a paid recurring layer.
- [ ] Keep ArcaneaClaw, stale OpenClaw forks, incomplete Hermes distributions, and README-only sales/marketing agents out of the partner catalog until their independent stop-ship findings are cleared.

**Exit gate:** a second operator can repeat the install without custom code and without receiving broad estate credentials.

## Explicitly deferred

- marketplace;
- public certification claims;
- autonomous wallet or x402 production spend;
- unattended publishing or outreach;
- broad OpenClaw/Hermes deployment;
- multi-vertical SaaS platform;
- enterprise dashboard;
- production DNS or billing changes without named approval.
