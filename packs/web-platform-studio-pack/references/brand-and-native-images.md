# Brand identity and native image generation

Identity is a system: name/voice, mark, typography, color, art direction, component language, imagery and consistent usage. A logo alone cannot establish the quality of a website.

## Native Codex image workflow

When running in Codex with its native image-generation tool, use that tool for raster concepts and image edits. Follow the installed imagegen skill and current tool contract. Do not require an API key for a native-tool workflow. API/CLI automation is a distinct integration with its own credentials, cost and user authorization.

1. Read the brand brief, existing approved identity, asset rights and taste feedback. Define audience, job, desired character, shapes to explore, exclusions, intended sizes and output formats.
2. Prepare a small set of materially different directions. For each, specify composition, geometry, typography treatment, palette and usage context. If existing imagery is supplied, inspect it and retain its source/permission.
3. Generate the requested concept using the native tool. Preserve the exact prompt, reference images, output path, timestamp, session, provider and actual model metadata returned. If seed/model metadata is unavailable, record that honestly instead of inventing a value.
4. Inspect the result at the intended size. Check letterforms, spacing, unintended symbols, edge artifacts, transparency and resemblance to the reference. Edit against the actual image when refining it.
5. Select a direction with the human brand owner. Build or refine a true SVG master when a vector identity is promised. A raster placed inside an SVG wrapper does not create a vector mark. Use the native vector/design workflow for existing vector assets.
6. Test the mark at small sizes, monochrome, dark/light surfaces, favicon, social/avatar crop and print when included. Check typeface licensing and record the exact final assets.
7. Package the editable source, SVG, raster exports, favicon set, color/type tokens, usage rules and provenance. Keep generated concepts separate from approved final identity.

A design similarity review helps identify obvious problems; it does not establish trademark clearance. Any promised clearance requires its own appropriate review. Never claim exclusivity over third-party assets or imitate a competitor's identity.

## Provenance and taste

The included example is a portable starting format. Follow the host's supplied sidecar schema and ledgers where present. In Starlight, every generated visual needs the adjacent `.vis.provenance.json` sidecar and entries in the existing image-generation and taste-feedback ledgers. Read prior aesthetic feedback before generation. Keep the exact prompt, returned metadata, output hash and acceptance decision. The example file by itself is not a generation receipt or schema validation.

## Website and launch asset family

Produce only assets that support the visitor's task: hero scene/product image, evidence screenshots, diagrams, editorial illustrations, social preview, icons, product/listing images and optional launch motion. Maintain a consistent subject, lighting, palette and composition across the family. Reserve real layout space and choose responsive crops, compression, dimensions and descriptive alternatives.

Photography-like scenes must not fabricate customer endorsements, facilities, certifications or product functionality. Label illustrative material where a viewer could reasonably mistake it for evidence. Product screenshots used as proof must come from the actual product.

## Reusable product opportunities

Package original identity systems, editable icon sets, art-direction recipes, image prompt/evaluation pairs, responsive asset pipelines and native design tokens. Differentiate by a complete usable visual system and demonstrated application. Keep rights and supported formats explicit. The source of value is the quality and usability of the delivered asset family.
